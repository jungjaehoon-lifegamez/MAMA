# 개발 작업의 목적 점검

이 문서는 개발자의 작업 기준이다. 실행 중인 MAMA의 승인 절차나 모델 실행 조건으로 사용하지 않는다.
제품 목적은 [INTENT.md](../../INTENT.md), 실행 구조는 [owner runtime 설계](one-mama-owner-runtime.md)를 따른다.

현재 최상위 성공 기준은 전체 수집 데이터의 축적, 쉬운 점진 접근, 현시점 정기보고,
오너의 후속 질문과 가능한 작업 수행, 결과의 다음 보고 반영이 이어지는 것이다.
아래 개별 항목의 성공으로 전체 흐름을 대신하지 않는다.

아래 v1의 시나리오와 관측값은 2026-09-07 당시 개발 기준이다. 상태는 최신 점검 기록으로 갱신하며,
검증 항목을 제품의 목적이나 매 행동의 선행 심사로 옮기지 않는다.

## 완료 기준 — 사용자 시나리오

시나리오의 ID와 성공 기준은 계획·작업·리뷰·체크포인트에서 그대로 인용한다.
증거 수준(단위/통합/후보 실제 모델/설치/실운영)을 결과와 따로 기록한다.
일부 경로만 통과하면 `부분 확인`, 실패가 있으면 `미충족`, 근거가 없으면 `미확인`이다.

상태는 위 날짜의 출발점이다. 이후 상태 변경과 근거는
[의도 점검 기록](docs/development/intent-checks.md)에 남긴다. 오래된 상태를 현재 확인 결과로
제시하지 않는다. 모든 필수 시나리오가 충족되기 전에는 최상위 목적을 완료로 선언하지 않는다.

## 작업 전·후 의도 점검

### 작업 시작과 전환 시

세션 시작/리쥼, 하위 결과 수령, 새로운 실패 발견, 작업 방향 변경 때 이 문서의 버전과
미해결 시나리오를 복원한다. 같은 세션에서 읽은 버전이 바뀌지 않았다면 전체 문서를
반복해서 읽지 않고 필요한 시나리오와 변경 부분을 참조한다.

작업을 시작하기 전에 기존 계획에 다음 세 가지를 적는다.

- 연결 시나리오: I-0N과 관련 TG-0N.
- 기대하는 사용자 행동 변화와 현재 실패 원인. 단순히 수정할 파일 이름으로 대체하지 않는다.
- 무엇을 실행·관측하면 변화가 입증되는지, 무엇은 그 증거만으로 판단할 수 없는지.

### 각 작업 완료 후 — 반드시 수행

1. 결과가 위 사용자 행동을 실제로 바꿨는지 증거로 확인한다.
2. 성공 기준을 줄이거나, 실제 흐름을 helper/mock으로 바꾸거나, 발견한 실패를 범위 밖으로
   밀어내지는 않았는지 확인한다.
3. 각 시나리오의 결과와 증거 수준, 아직 실패하거나 확인하지 못한 조건을 갱신한다.
4. `부합 / 부분 부합 / 불일치`를 판정하고 [의도 점검 기록](docs/development/intent-checks.md)에
   짧게 남긴다. 부분 부합·불일치는 원래 목적을 유지한 채 다음 작업을 조정한다.
5. 완료 보고에서 하위 작업 완료와 최상위 목적 완료를 구분한다. 테스트 개수만 보고하지 말고
   이제 성공하는 시나리오와 남은 실패를 먼저 말한다.

리뷰어에게도 diff의 타당성뿐 아니라 해당 시나리오의 충족과 검증의 충실도를 묻는다.
하위 에이전트에게는 목적 한 문장, 연결 시나리오, 종료 조건, 필요한 근거·담당 범위를 전달한다.
결과 통합과 최상위 목적 판정은 부모 에이전트의 책임이다.

## 설치·릴리즈와 리쥼

- 설치·릴리즈 전에 후보에서 대표 실패를 재현하고 수정 전후를 비교한다. 사용자에게 약속한
  범위의 증거가 부족하면 완료·릴리즈 준비 완료로 선언하지 않는다.
- 배포 후 확인은 설치·환경 차이와 회귀를 확인한다. 제품 개선을 처음 증명하는 단계로 쓰지 않는다.
- 사용자가 제한된 후보 설치를 명시적으로 요청하면 그 범위와 남은 실패를 보존한다.
  설치됐다는 이유로 시나리오나 최상위 목적을 충족으로 바꾸지 않는다.
- 체크포인트에는 이 문서의 버전/위치, 시나리오별 상태·근거·미해결 조건, 다음 작업이 목적과
  연결되는 이유를 저장한다. 리쥼은 마지막 파일 수정이 아니라 이 기준의 복원부터 시작한다.
- 새 사용자 지시로 목적이 바뀌면 변경 이유와 영향을 이 문서에 명시하고 기존 계획을 맞춘다.
