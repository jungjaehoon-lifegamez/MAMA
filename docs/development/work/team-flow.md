# Team flow — from enrollment to revoke, for the first member

One analysis of the whole member flow, merged from two independent read-only reviews (Codex
`gpt-6.1-sol` and a Claude Opus subagent, 2026-10-07) and checked against the code where it
changes the result. Only program problems count: what a better model would fix is not product
work (AGENTS.md). Evidence and measurements go to [checks](../checks.md).

**The result in one sentence:** core already has principals, grants, many principals per runtime,
a per-turn access hook and a write/read scope split, but the product wires every principal-
dependent path to the owner, and two core gaps block a read-only member before any wiring.

## Settled decisions

- 2026-10-06: separate agent sessions for the common session, the owner session and each member;
  common memory is kept apart from each member's memory.
- 2026-10-06: the owner's agent cannot read a member's chat by default.
- 2026-10-07: the owner cannot see a member's personal records (chat, memory bound to the member,
  unshared work, workspace files) unless the member allows it. Members get document and image
  work through their agent: native file and shell tools inside a workspace of their own.
- 2026-10-06: no separate feedback-forwarding route; forwarding to a team destination is delivery.
- Telegram first. Enrollment by owner forward (`forward_origin.sender_user.id`, chosen 2026-08-15);
  an owner-issued invite link is the alternative to compare.
- The personal agent reads granted common work and the member's own work to explain priorities;
  the shared agent coordinates common work. Common work keeps one ledger and one revision chain.
- Live since 2026-10-06: chat stored as raw sources bound to `user:<principal>` (W38); standing
  owner rules in owner-policy.md (W37).

## First-member slice

One real member, Telegram DM only, personal memory, read-only access to granted common work,
document and image work in the member's own workspace, the owner unable to see the member's
personal records. The admission switch is last, so no member input arrives
before the boundaries exist. Core steps need a core release before the product steps that use them.

## Decisions needed before the slice, in blocking order

1. Enrollment path: owner forward, or invite link with owner approval (blocks step 3).
2. Partition unit for common work and the default for unscoped writes (blocks steps 4–5).
3. The member's action set for the slice: a fixed read-only role, or per-member grants (blocks step 4).
4. Native isolation: a member workspace outside the owner's home with the home denied for reads,
   under one OS user; or a separate OS user (blocks step 7). Catalog tools only is out: members need
   document and image work (owner, 2026-10-07).
5. Consent: a member shares an item in their own turn (an appended revision binds it to a shared
   scope), or grants the owner standing read of their scope (core grants need an owner grantor
   today) (blocks step 8).

Can wait until the step that needs them: the serial chain or lanes (step 6); owner policy text in a
member session (step 6); revoke
semantics and workspace files (step 10); DM updates to common work, approval, destinations (after
the read-only slice).
