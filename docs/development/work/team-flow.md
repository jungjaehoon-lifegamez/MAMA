# Team flow — from enrollment to revoke, for the first member

One analysis of the whole member flow. Two independent read-only reviews wrote it (Codex
`gpt-6.1-sol` and a Claude Opus subagent, 2026-10-07); a second pair reviewed the plan itself the
same day, and every point that changes the plan was checked in the code. Only program problems
count: what a better model would fix is not product work (AGENTS.md). Evidence goes to
[checks](../checks.md#team-plan-review-codex-and-opus-2026-10-07).

**The result in one sentence:** core already has principals, grants, many principals per runtime,
a per-turn access hook and a write/read scope split, but the product wires every principal-
dependent path to the owner; in core, work and graph reads ignore read grants, a revision rebinds
its item to the writer's scopes, and nothing can export or erase a member's records.

## Settled decisions

- 2026-10-06: separate agent sessions for the common session, the owner session and each member;
  common memory is kept apart from each member's memory.
- 2026-10-06: the owner's agent cannot read a member's chat by default.
- 2026-10-07: the owner cannot see a member's personal records (chat, memory bound to the member,
  unshared work, workspace files) unless the member allows it. Members get document and image
  work through their agent: native file and shell tools inside a workspace of their own.
- 2026-10-07: a member's own computer connects through MCP and exposes only the drives or
  folders the member chooses; members' personal files do not go up to a Drive folder MAMA reads
  with the owner's account.
- 2026-10-07: first members keep their personal records on the MAMA Mac behind this boundary,
  and each member can export all their personal records to their own computer and delete them
  from the server. A member's own MAMA on their computer comes later.
- 2026-10-06: no separate feedback-forwarding route; forwarding to a team destination is delivery.
- Telegram first. The personal agent reads granted common work and the member's own work to
  explain priorities; the shared agent coordinates common work. Common work keeps one ledger and
  one revision chain.
- Live since 2026-10-06: chat stored as raw sources bound to `user:<principal>` (W38); standing
  owner rules in owner-policy.md (W37).

## Decided on 2026-10-08

The owner took every recommendation.

1. Enrollment (P7): a `request_users` button in the owner's DM; the host reads the chosen id, no
   token store. The owner forward chosen on 2026-08-15 is dropped (a hidden forward carries no
   id). Unenrolled senders get no reply.
2. Partition and default (P1–P2): one scope per project with ids of its own, not connector names;
   a member's unscoped write binds `user:<member>`; the owner's default is unchanged.
3. Member role (P1): one fixed role: read granted work, personal memory, share, file delivery to
   the own DM; no common-work writes, owner policy, Drive or reports.
4. Native isolation (P4): one OS user; the member workspace outside the owner's home, the home
   denied. A failed smoke test (a member's sandboxed DB read succeeding, or file tools failing
   under the deny) moves it to a separate OS user.
5. Consent (P2b): per-item share in the member's own turn; the owner binds common work to partitions in P2a. A shared item shows its whole revision
   history, stated in the share action's description; the graph then admits that history for the
   reader (the #445 links-view finding).
6. Erasure (B1, P9): an exception to INTENT.md's "records and links are never edited" for records
   bound only to the member's own scope: delete what nothing shared cites, tombstone what it cites.
7. Member alerts (P6): no web tools for members in the slice; a refused connection from a member
   session alerts the owner with the principal, host and time only.
8. Member computer (after the slice): processing on the MAMA Mac; a private network (Tailscale,
   one-time key); an SFTP-only account limited to the chosen folders; no delete; an unreachable
   computer fails loud.
9. Shared changes in the open (2026-10-09): owner policy and shared records (partition-bound common
   work and shared copies) change in a group room, where enrolled members may change them too,
   recorded by principal. A member's own chat changes only its own records (#457); it may still
   share one. The owner keeps changing them from the owner's chat.
10. The owner agent's read boundary (2026-10-09, P6): the owner agent and its subagents do not read
    a member's personal records unless the member shares them. They read records through MAMA
    actions under the owner's access; native reads of the product DB, the raw stores,
    `member_root` and the member temp root are denied. Everything else stays unrestricted.
    Recorded in AGENTS.md (#460).
11. The first member is a co-owner (2026-10-09, P7; revised by the owner 2026-10-10: the owner need
    not be one person): that person's Telegram id stays in `owner_user_ids` and bound to the owner
    principal. MAMA treats both people as the one owner: shared memory, owner-rule authority and
    enrollment, and no P6 boundary between them. Core keeps one active owner principal
    (`principal-repository.ts:284-286`); several people are several identities bound to it.
    Enrollment refuses an id listed in `owner_user_ids`; P10 must keep refusing it after the key
    goes. The real member checks of P8–P10 need another person or a test account; the directory the
    P4 smoke made under that person's member id is unused. `member_root` is the shared directory
    the P4 smoke used, outside the owner's home (set 2026-10-10). Enrollment is identity only;
    partition grants are a later owner action.
12. Revoke (2026-10-10, P8): owner-only actions in the owner's own message turn revoke a member's
    partition grant, suspend, resume and offboard; never the owner principal, co-owners included.
    Each runs on the shared serial chain and takes effect after the member's running turn, so a
    receipt means the change is in force. A grant revoke resets the member's native session and
    keeps its workspace files: copies already made stay, like anything the member has already
    seen. Suspend and offboard end the session and set the member's runtime directory aside, not
    deleted; resume brings a suspended member back with its grants in a fresh environment. Offboard
    is final: every grant is revoked, and the Telegram identity binding stays as a record, so the
    same id is not enrolled again. Queued member inputs at a revoke are cancelled with a host
    reason. Export and erase of personal records stay in P9. Restart recovery for member messages
    moves to P10, where member messages first arrive. Added the same day: the same actions grant a member a project
    partition read and list members (principal, status, grants; never a Telegram id); source-channel
    grants are not offered.
13. Export and erase (2026-10-11, P9): a member erases its personal records only from its own
    message turns, and only after confirming in a later member message than the one that asked;
    the host checks the turn, not the model. Erasure always exports first: after the confirming turn
    settles, the host sends the whole export to the member's DM and erases only once Telegram
    confirms delivery; a failed or oversized delivery erases nothing. The member stays enrolled
    with its grants and starts again in a fresh environment; erasure is not offboard. Work list:
    [member-erasure.md](member-erasure.md#product-p9-owner-decision-13-2026-10-11). Merged
    (#471). Left for P10: recovering a member-DM receipt after a restart, keeping a confirmed
    erasure across a restart, and pausing claims for the erasing member only (an erasure now
    pauses every claim until its export is delivered).

Settled at P3 by the design: one shared serial chain, and no owner policy text in a member session
(the role holds no owner policy). Can wait until the step that needs them: workspace files beyond
decision 12; DM updates to common work, approval, team destinations (after the slice).
