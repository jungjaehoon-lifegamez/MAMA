# Approvals — a write the agent proposes runs after an owner approves it in Telegram

Status: design, not built. Owner decisions, 2026-11-17:

- The agent may propose a write in any turn, including turns with no person in them (source
  deltas, reports, jobs). The write runs only after an owner approves it in Telegram.
- The scope is every kind of work, so the approval step is one mechanism every write goes through,
  not one per feature (approach C below).
- Anyone with the owner role may approve a card in the common channel.
- Accounts are per person. A write runs as the account of the session that proposed it: the common
  session uses the accounts the install connected; a person's DM uses the accounts that person
  connected, and only that person approves it. Nobody's write runs on another person's account.
- Codex app writes run only in a turn an owner's own message started (B1). Turns with no person in
  them propose MAMA actions only. This changes Codex's approval policy from `never` (driver,
  managed config, AGENTS.md) for the common session's thread, with every request outside an owner
  message turn still declined by the host.
- Kakao and LINE keep Kagemusha's Android method and live in a private package. MAMA's public
  repository carries the approval step and a place to attach an external connector; nothing this
  work adds names Kakao or LINE (the existing `kagemusha` source and its replay import stay as
  they are). Public desktop tools (kmsg, kakaocli) are not used: they need a
  desktop window and run on macOS only.

This serves INTENT's "forwards feedback and files" and "does the work": today the agent can tell
the owner what to send, and cannot send it.

## Why writes are closed today

Turns with no person in them run as the common owner and read text other people wrote. A write
open to those turns can be driven by text in a source (#582's security review). So
`google.calendar.write` runs only in a turn an owner's own message started, and Codex apps are
read only (#583). The approval step is what lets those turns act: the agent proposes, a person
decides.

## Program evidence

- **nh's order approval** (a separate local project; mechanism only is ported): the agent can only
  prepare a proposal, with a strict input shape and a request key that makes a repeat return the
  same card. The host stores the intent with a fingerprint and a one-time nonce, renders the card
  from the stored intent, and sends it with Approve and Reject buttons whose callback data is
  `<kind>:<a|r>:<id>:<nonce>` (64 bytes at most). The button press never reaches the model: the
  host checks the presser, the nonce (timing-safe), the fingerprint, the status and the expiry,
  then moves `proposed → approved → submitting → accepted | failed | unknown`. A repeated press
  answers from the stored state. A submission interrupted by a restart becomes `unknown` and is
  never sent again; the owner is told to check.
- **Telegram gateway**: handles `message` updates only (`gateways/telegram.ts`); no inline keyboard
  or `callback_query` handler exists. The only button is enrollment's `request_users` reply
  keyboard.
- **Two-step confirmation exists once**: record erasure previews, issues a token and takes the
  confirmation in a later member message (`api/member-records.ts`). The model carries the token.
- **Codex app writes ask for approval** (measured on Codex CLI 0.160.1, `approval_policy =
"on-request"`): the app-server sends `mcpServer/elicitation/request` with
  `_meta.codex_approval_kind = "mcp_tool_call"`, `connector_name`, `tool_title` and `tool_params`
  (the full arguments). The driver answers every such request `decline` today
  (`codex-app-server-process.ts`), and a declined call fails with `user rejected MCP tool call`.
  Under `approval_policy = "never"` the call fails without asking.
- **Codex's approval policy is set in three places**: the driver sends `approvalPolicy: 'never'` on
  thread start and resume and throws on any other answer (`codex-app-server-process.ts`); the
  managed config writes `never` whenever denied read paths are passed, which the owner runtime
  does (`codex-home.ts`); and AGENTS.md's isolation table pins Codex approvals to `never`. The
  policy is per thread, and the common session's one thread also runs the turns with no person in
  them. The driver also accepts Codex's own reviewers (`auto_review`, `guardian_subagent`).
- **A turn's idle timer does not wait for an answer**: it restarts only on items, deltas and tool
  calls, not while a server request is pending, and `mama init` writes `agent.timeout` as 10
  minutes.
- **Sending**: Chatwork's API token also posts messages, as the token's owner. Slack's gateway
  already calls `chat.postMessage`, as the bot. Kagemusha sends Kakao and LINE by driving the app
  in an Android emulator over ADB, finding the room by name (`sendAdbMessage`).
- **Connectors load from a fixed list** (`LOADABLE_CONNECTORS`); an unknown name is refused.

## Approaches

|                | What                                                                                                                                       | Trade-off                                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| A              | `approval.propose` over MAMA's own actions: the host validates and stores the input, shows a card, and runs the stored input when approved | Both backends; the turn does not wait, so an approval hours later works. Covers only the write actions MAMA has |
| B              | Codex's own app approval request is shown as the card and answered from the button                                                         | Hundreds of app writes at once. The turn waits for the answer; Codex only; the card shows what Codex sends      |
| **C (picked)** | A is the base; B's requests go through the same store, card and button                                                                     | Widest; costs both builds                                                                                       |

## What the owner sees

```
Approval request · Google Calendar: create event
Title: Review
When: 11/20 (Fri) 10:30–11:00 Asia/Seoul
Attendees: person@example.com (invitation is sent)
Meet link: yes
Proposed from: source change, 09:57
Expires: 11/18 09:58
[Approve] [Reject]
```

After a press the buttons go and one line is added: who decided, when, and the result (the event
link, the message link, or the failure).

## Left to the builder (my calls, not owner decisions)

- The canonical form for the fingerprint: sorted keys, as nh's `canonical`.
- The card is plain text plus the keyboard, rendered by the host; Telegram HTML only for the title
  line.
- `reason` is the agent's one line on why it proposes; it is shown under a "Proposed from" label
  and is never part of what runs.
- A proposal the owner wants changed is rejected and proposed again; the card itself is not
  edited.
- Approval lives on Telegram only. Discord and Slack owner messengers are experimental and get no
  cards.

## Not built

- "Always allow" for an action or a destination. Every write asks.
- Approving several proposals with one press.
- Payments, purchases and browser control.
- A send for Gmail, Sheets or Docs as MAMA actions: on Codex they come with B1; on Claude they are
  added one at a time when the owner asks for one.

## Risks named

- **A card can look right and still be wrong** when the input names a room or person by an id the
  owner cannot read. Each `approvalCard` resolves ids to names from the host's own data and shows
  both.
- **B1 changes the managed Codex approval policy.** If any other request kind starts being
  accepted, the sandbox is weaker than today. That is why B1's first step is a measurement.
- **Kakao and LINE sends cannot confirm delivery** beyond what the app's screen shows, and the
  method is against those services' terms. That risk stays in the private package and with its
  owner.
